# E3.1 — Material Fast Setup

Ускорение ввода материалов без AI. AI-скан, OCR и распознавание накладных в эпик
не входят и не подготавливались — абстракций «на будущее» здесь нет намеренно.

## Что осталось в продукте

| Часть | Где |
|---|---|
| F1. Каталог шаблонов | `material_template` (миграции 0034 и 0037), [seeds/material-templates.json](../seeds/material-templates.json), [lib/material-templates.ts](../lib/material-templates.ts), `GET /api/v1/material-templates`, `POST /api/v1/materials/from-templates` |
| F2. Aggregate | `material.kind`, [domain/material-provenance.ts](../domain/material-provenance.ts) |
| F5. Provenance | `material.source`, `material_price_version.price_source`, бейдж в карточке материала |

Шаблон выбирается поиском в форме добавления материала
([components/material-catalogue.tsx](../components/material-catalogue.tsx)):
список сгруппирован по 11 категориям, выбор строки подставляет название,
единицу и типовой объём упаковки — объём остаётся редактируемым, цену вводит
владелец.

## Что удалено 15.08.2026

**F3 Fast Setup** и **F4 bulk paste** удалены по решению владельца продукта:
экран быстрой настройки, вставка списка, эндпоинты `bulk-paste/parse` и
`bulk-paste/confirm`, доменный парсер вставки, их компоненты, тесты и ключи
i18n.

Удалено из кода, но **не из базы**: `material_template`, `material.kind`,
`material.source`, `material.template_id`, `material_price_version.price_source`
и `booking_idempotency_key.result` на месте и используются оставшимися частями.
Отдельной миграции на снятие не требуется.

Что осталось от этой работы и продолжает приносить пользу CSV-импорту:

- синонимы единиц (`мл`, `шт`, `buc`, `гр`) в [domain/import-templates.ts](../domain/import-templates.ts);
- `positive: true` у объёма упаковки: `0` теперь `not_positive` на валидации,
  а не `write_failed` на check-констрейнте;
- `409 MATERIAL_EXISTS` вместо 500 при совпадении natural key.

## Принятые решения

### Схема отличается от эскиза в постановке

Эскиз в задании написан под другую схему. Расхождения и что сделано вместо:

- **`numeric(12,3)` → milli-units.** Проект хранит все количества целыми
  тысячными ([domain/units.ts](../domain/units.ts)); инвариант «деньги и
  количества — целые» сильнее, чем форма колонки в эскизе.
- **`material_price_history` → `material_price_version`.** Таблица уже есть и
  уже append-only.
- **Natural key без `package_quantity`.** Фасовка живёт в
  `material_price_version` и меняется во времени — включить её в ключ материала
  нельзя. Ключ: `(organization_id, match_key, base_unit) WHERE archived_at IS NULL`.
- **`match_key` считается по `name`, не по `brand || name`.** У материала нет
  колонки бренда: бренд принадлежит шаблону. Если бы бренд входил в ключ, два
  материала «База» сосуществовали бы, пока один из них помнит другой шаблон —
  ровно тот дубль, ради которого ключ вводится.
- **`pg_trgm` не добавлен.** 85 строк каталога фильтруются в памяти, а «похожий
  материал существует» решается через `match_key`. Extension ради этого —
  инфраструктурная зависимость без выигрыша.

### `unit_cost` не хранится и не округляется заранее

Требование §3.2 выполнялось до этого эпика: `materialCostMinor()` округляет
один раз, в конце. Проверка `185.00 MDL / 15 ml`, расход `0.6 ml` → `7.40 MDL`
живёт как тест в [domain/units.test.ts](../domain/units.test.ts). Публичный
контракт Costing Engine не менялся.

### Шаблон несёт `system_key`

Неочевидная, но обязательная связка: пресеты рецептур
([domain/material-presets.ts](../domain/material-presets.ts)) находят материалы
по `material.sku = 'SYSTEM:<key>'`. Материал из шаблона получает **и**
`template_id`, **и** `sku`. Без этого Fast Setup создал бы 14 материалов, а
пресеты рецептур их бы не увидели, и владелец закончил бы онбординг с
каталогом, который ничего не стоит.

### Идемпотентность: колонка `result`

`booking_idempotency_key` уже была generic по `scope`, но хранила только
`booking_id`. Создание пачки материалов из шаблонов не указывает на одну строку,
поэтому добавлена `result jsonb`. Таблица **не переименована**: переименование —
единственное изменение в 0034, которое плохо откатывается.

### Телеметрия — только серверная

`material_entry_started` и `material_form_abandoned` из §3.5 браузерные, а
эндпоинта для клиентской телеметрии в продукте нет. Пишутся серверные:
`material_saved`, `material_price_updated`, `fast_setup_completed`.
Имена `bulk_paste_confirmed` и `fast_setup_completed` остались в
`PilotEventName`, хотя пишется теперь только второе.

Режим передаётся булевыми флагами и счётчиками, а не строкой (`{ template: true,
bulk_paste: false, fields_prefilled: 4 }`), потому что `metadata` в этом проекте
принимает только числа и булевы значения. Ни названий материалов, ни абсолютных сумм в событиях нет.

## Сознательные упрощения

- **Один материал на `system_key`.** Шаблон, чей ключ уже занят, не предлагается
  и не создаётся. *Триггер:* пилотной студии понадобится две базы с разными
  ценами — тогда сопоставление пресетов должно уметь выбирать.
- **Разбивка материалов в P&L группирует по имени.**
  [lib/period.ts](../lib/period.ts) сопоставляет `materialNameSnapshot` со
  списком `starterMaterials`, поэтому брендированные материалы попадают в
  «материалы для ногтей». Generic-шаблоны названы точно как starter-список
  (закреплено тестом), так что Fast Setup разбивку не ломает. *Триггер:*
  когда брендированных материалов станет большинство — снапшотить категорию.
- **Down-миграция написана только для 0034.** Остальные 33 остаются без отката —
  это отдельная работа, не относящаяся к эпику.

## Каталог: фиксированный системный список (15.08.2026)

`seeds/material-templates.json` — **85 родовых позиций в 11 группах**, заданных
владельцем продукта. Прежний каталог на 155 записей со 114 брендами заменён
целиком; сид удаляет строки, которых нет в файле.

Три свойства этого списка стоит держать в голове.

**Фасовка — редактируемое значение по умолчанию.** `package_size_milli_units`
стала nullable (миграция 0037), но у всех 85 записей проставлен типовой объём:
База 15 мл, Гель-лак 8 мл, Builder Gel 30 г, Перчатки 100 шт. Это **не
утверждение о поставщике**: «База» продаётся в 8, 12, 15 и 35 мл, поэтому цифра
подставляется в поле формы и владелец переписывает её под ту упаковку, которую
купил. Приоритет всегда за введённым значением; каталожное подставляется, только
если поле не тронули. Колонка остаётся nullable, чтобы будущая позиция могла
честно сказать «не знаю» — тогда создание отклоняется кодом
`PACKAGE_SIZE_REQUIRED`, а не подставляет выдуманное число.

**Единица есть у каждой позиции.** В отличие от фасовки, единица измерения не
меняется от упаковки к упаковке: антисептик всегда в мл, перчатки всегда
поштучно. Её каталог задаёт, и выбор позиции её подставляет.

**`system_key` только у девяти записей** — тех, чьё имя точно совпадает со
`starterMaterials`: Дегидратор, Масло для кутикулы, База, Гель-лак, Топ, Стразы,
Перчатки, Ватные диски, Фольга для снятия. Остальные 76 его не получают, и это
осознанное решение владельца продукта: пресеты рецептур
([domain/material-presets.ts](../domain/material-presets.ts)) ищут материал по
`sku = 'SYSTEM:<key>'`, а разбивка материалов в отчёте
([lib/period.ts](../lib/period.ts)) группирует по имени — обе механики работают
только на этих девяти. Расчёт себестоимости не затронут: он читает цену и
фасовку самого материала. Ключ, назначенный «по смыслу», направил бы пресет на
другой ингредиент, поэтому привязка сделана только по точному совпадению.

Бренды: колонка `material_template.brand` осталась в схеме, но у всех записей
пуста — новый список брендов не содержит.

## Права на `material_template` (миграции 0035 и 0036)

0034 создала таблицу — и на Supabase создала её **не той ролью**.
`MIGRATION_DATABASE_URL` в этом развёртывании подключается как `postgres`, а
`ALTER DEFAULT PRIVILEGES` в `scripts/supabase-init.sql` выставлен от имени
`nail_profit`. Права по умолчанию записываются на роль-создателя, поэтому новая
таблица получила:

- ноль прав для `nail_profit_app` — приложение не могло её прочитать, и
  `/app/materials` падала с `permission denied` при каждом рендере;
- полный набор грантов Supabase для `anon`, `authenticated` и `service_role` —
  то есть таблица была видна через PostgREST.

`REVOKE` в 0034 при этом не отзывал ничего: отзывать было нечего. Он выглядел
защитой, не будучи ею.

0035 передаёт владение `nail_profit`, закрывает `anon`/`authenticated`/`PUBLIC`
и выдаёт `SELECT` роли приложения явно, не полагаясь на права по умолчанию.
0036 доотзывает `service_role` — третью роль Supabase, которую 0035 пропустила,
а `scripts/verify-rls.sql` проверяет.

В `verify-rls.sql` добавлена структурная проверка **1c**: приложение обязано
читать каждую таблицу в `public`. Проверка 1b (экспозиция в PostgREST) уже
существовала и в комментарии обещала ловить оба симптома, но отсутствие грантов
у роли приложения не проверяла — из-за чего падение и не было предсказано.

## Побочные исправления

- `POST /api/v1/materials` отвечает `409 MATERIAL_EXISTS` вместо 500 при
  совпадении natural key.
- `package_size = 0` в импорте теперь `not_positive` на этапе валидации, а не
  `write_failed` на check-констрейнте.
- Синонимы единиц и `positive` доступны всему CSV-импорту, не только вставке.

## Команды

```bash
npm run db:migrate:test && npm run db:migrate:down:test && npm run db:migrate:test
```

```bash
npm run db:seed:templates:test && npm run db:seed:templates:test
```

Варианты с `:test` читают `TEST_MIGRATION_DATABASE_URL` и отказываются работать
с базой, чьё имя не заканчивается на `_test`
([drizzle.test.config.ts](../drizzle.test.config.ts)). Это не удобство, а
защита: `drizzle-kit` подгружает `.env` **после** переменных оболочки, поэтому
`MIGRATION_DATABASE_URL=<тестовый url> npx drizzle-kit migrate` на этом
репозитории уходит в базу из `.env`.

## Что не сделано

- Клиентская телеметрия friction (нужен эндпоинт приёма событий).
- Автоматический merge похожих материалов — по постановке только подсказка.
- Складской учёт, остатки, AI-распознавание — вне эпика.
- F3 и F4 — см. «Что удалено» выше.
