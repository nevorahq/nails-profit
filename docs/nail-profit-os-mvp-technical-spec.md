## 1. Назначение документа

Документ определяет продуктовые и технические требования к первой версии Nail Profit OS. Он служит общей основой для product owner, UX/UI-дизайнера, backend- и frontend-разработчиков, QA и DevOps.

MVP должен доказать три гипотезы:

1. продукт помогает вернуть клиента в ожидаемый цикл повторного визита;
2. продукт помогает заполнить слот после отмены и измеряет восстановленную выручку;
3. продукт рассчитывает себестоимость услуги и показывает реальную contribution margin.

MVP не должен заменять Fresha, Booksy, YCLIENTS или другую полноценную систему записи. Он реализуется как **Nail Profit Layer**: самостоятельный web-продукт с минимальным контуром визитов и открытым слоем импорта, который можно использовать поверх действующей системы записи.

### 1.1. Текущее состояние

На дату документа продуктовая реализация отсутствует. В рабочей папке есть только стартовый web-каркас без доменной логики Nail Profit OS. Поэтому ТЗ описывает greenfield-систему, а рекомендуемый стек не является ограничением существующей архитектуры.

## 2. Термины

| Термин | Определение |
|---|---|
| Организация | Изолированный аккаунт мастера, студии или небольшой сети. Технически это tenant. |
| Локация | Физическая точка оказания услуг. В Solo-тарифе создаётся одна локация. |
| Специалист | Мастер, выполняющий услуги. Может иметь доступ пользователя или существовать только как объект учёта. |
| Рабочее место | Стол, кабинет или иной ограниченный ресурс, необходимый для визита. |
| Запись | Запланированный временной слот клиента у специалиста. |
| Визит | Фактически оказанная или отменённая услуга с финансовым результатом. |
| Add-on | Дополнение к базовой услуге: снятие, укрепление, френч, ремонт, дизайн и т. п. |
| Рецептура услуги | Нормативный набор материалов и их количество для услуги или add-on. |
| Contribution margin | Выручка за вычетом комиссии мастера и фактической стоимости материалов и расходников. |
| Ожидаемая дата возврата | Рассчитанная системой дата следующего визита клиента. |
| Потерянный клиент | Клиент, который не записался в течение допустимого периода после ожидаемой даты возврата. |
| Waitlist | Список клиентов, готовых прийти в определённые дни, интервалы и/или к конкретному мастеру. |
| Slot Protection | Набор правил и автоматизаций, уменьшающих потери от поздних отмен и пустых часов. |
| Восстановленная выручка | Выручка от завершённого визита, созданного для заполнения конкретного отменённого слота. |
| Внешняя запись | Запись, импортированная из другой CRM, календаря или файла. |

## 3. Цели и показатели успеха

### 3.1. Цели MVP

- дать владельцу ответ на вопрос «сколько я действительно заработал»;
- показать прибыль по услугам, специалистам и рабочим местам;
- выявлять клиентов, которым пора вернуться;
- позволить отправить персональное предложение и записать клиента по защищённой ссылке;
- быстро предлагать освободившийся слот подходящим клиентам;
- учитывать фактический и нормативный расход материалов;
- работать без обязательной миграции с текущей CRM.

### 3.2. Целевые продуктовые KPI пилота

| KPI | Цель для пилота | Метод измерения |
|---|---:|---|
| Time to first value | до 30 минут | От создания организации до первого рассчитанного прибыльного визита |
| Доля визитов с рассчитанной маржой | ≥ 80% | Завершённые визиты, для которых определены выручка и переменные затраты |
| Доля клиентов с прогнозом возврата | ≥ 80% | Клиенты с завершённым визитом и достаточными данными |
| Rebooking conversion | базовая линия +10% | Доля предложений, завершившихся подтверждённой записью |
| Cancellation recovery rate | ≥ 20% | Отменённые слоты, заполненные через Slot Protection |
| Активность владельца | ≥ 3 дней в неделю | Организации пилота с ключевыми действиями |
| Качество импорта | ≥ 99% валидных строк | Валидные записи без ручного исправления после импорта |

Цели пилота являются гипотезами и не входят в технические критерии приёмки релиза.

## 4. Границы MVP

### 4.1. Входит в MVP

- responsive web-приложение для desktop, tablet и mobile browser;
- организации, пользователи, роли, одна или несколько локаций;
- клиенты, специалисты, рабочие места, услуги и add-ons;
- минимальный календарь записей и визитов, необходимый для аналитики и самостоятельной работы;
- импорт данных из CSV и API-контракт для будущих CRM-коннекторов;
- история визитов и фотографии работ;
- параметры nail-дизайна;
- deterministic-прогноз следующего визита;
- персональные rebooking-напоминания и reactivation-кампании;
- cancellation policy, waitlist и заполнение освободившегося слота;
- материалы, единицы измерения, рецептуры и фактическое списание;
- себестоимость, комиссия мастера, contribution margin и прибыль в час;
- dashboard и выгрузка основных отчётов;
- русский, румынский и английский интерфейс;
- MDL и EUR;
- базовый audit log критичных действий.

### 4.2. Не входит в MVP

- consumer marketplace и публичный каталог всех мастеров;
- полноценный POS, касса и фискализация;
- сложный payroll и расчёт налогов;
- мобильные приложения iOS/Android;
- AI virtual try-on и AI-анализ референса;
- procurement marketplace;
- academy/LMS;
- сложные сетевые процессы для десятков локаций;
- медицинские анкеты и обработка специальных категорий персональных данных;
- двусторонняя синхронизация со всеми salon CRM;
- собственная омниканальная доставка сообщений;
- бухгалтерский P&L и распределение всех постоянных расходов.

### 4.3. Обязательные платформенные функции

Хотя они не являются продуктовыми модулями, MVP не может работать без:

- регистрации и входа;
- восстановления доступа;
- приглашения сотрудников;
- ролевой модели;
- настройки организации, локации, часового пояса и валюты;
- согласия с условиями и политикой конфиденциальности;
- журналирования критичных изменений;
- экспорта и удаления данных по запросу владельца.

## 5. Допущения, требующие подтверждения

1. Первый релиз является мультиарендным B2B SaaS: данные каждой организации строго изолированы.
2. Основной часовой пояс пилота: `Europe/Chisinau`; каждая локация хранит собственный IANA timezone.
3. Базовая валюта задаётся на уровне организации. Отчёты MVP не конвертируют валюты по курсу.
4. Денежные суммы хранятся в минимальных единицах валюты целыми числами, например 125.50 MDL как `12550` bani.
5. Обязательный канал уведомлений MVP: email. Один дополнительный transactional-канал, SMS или WhatsApp, подключается через внешний провайдер после коммерческой проверки. Остальные каналы используют тот же adapter contract позже.
6. Для режима «поверх существующей записи» гарантируется CSV-импорт и идемпотентный Import API. Конкретный live-коннектор к CRM выбирается отдельным решением после подтверждения доступности API и условий партнёрства.
7. Прогноз возврата в MVP основан на правилах и истории визитов, без machine learning.
8. Медицинские сведения, аллергии и диагнозы не собираются.
9. Фото хранятся только при наличии подтверждённого согласия клиента на соответствующую цель: внутренняя история и/или маркетинговое использование.

### 6.2. Изоляция данных

- каждая бизнес-сущность содержит `organization_id`;
- пользователь может обращаться только к организациям, в которых состоит;
- cross-tenant ID в запросе возвращает `404`, а не раскрывающий наличие объекта `403`;
- фоновые задания и импорты выполняются в контексте одной организации;
- файлы хранятся с tenant-scoped ключами и выдаются только через временные signed URL.

## 7. Основные пользовательские сценарии

### UC-01. Первый расчёт прибыльности

1. Owner создаёт организацию и выбирает язык, валюту и часовой пояс.
2. Добавляет специалиста, рабочее место и услугу.
3. Добавляет материалы и нормативы расхода либо пропускает шаг с явным предупреждением.
4. Импортирует или создаёт завершённый визит.
5. Система рассчитывает выручку, комиссию, материальные затраты, contribution margin и прибыль в час.
6. Dashboard показывает результат и список недостающих данных.

### UC-02. Возврат клиента

1. После завершения визита система рассчитывает ожидаемую дату следующего посещения.
2. За заданное число дней до даты создаётся задача на напоминание.
3. Клиент получает персональную ссылку с подходящими слотами.
4. Клиент выбирает слот и подтверждает запись.
5. Запись создаётся атомарно, если слот всё ещё свободен.
6. Кампания и прогноз получают статус `converted`.

### UC-03. Реактивация потерянного клиента

1. Клиент превышает ожидаемую дату возврата плюс grace period.
2. Он появляется в списке «Потерянные клиенты» с причиной и потенциальной выручкой.
3. Manager выбирает клиентов, шаблон и окно отправки.
4. Система проверяет согласие, quiet hours и frequency cap.
5. Уведомления отправляются через выбранный канал.
6. Система связывает последующую запись с кампанией для измерения конверсии.

### UC-04. Заполнение отменённого слота

1. Запись отменяется вручную или через Import API.
2. Система применяет cancellation policy и определяет, является ли отмена поздней.
3. Создаётся открытый slot recovery case.
4. Система подбирает waitlist-кандидатов по длительности, услуге, специалисту, локации и предпочтениям времени.
5. Manager подтверждает рассылку или автоматическое правило запускает её само.
6. Первый подходящий клиент, завершивший подтверждение, получает слот.
7. Остальные ссылки становятся недействительными, клиенты получают нейтральный статус «слот уже занят».
8. После завершения нового визита сумма учитывается как восстановленная выручка.

### UC-05. Фактический расход материалов

1. При создании визита система копирует нормативную рецептуру услуги и add-ons.
2. После процедуры Master подтверждает расход либо корректирует количество.
3. Система списывает фактическое количество и рассчитывает variance к норме.
4. Прибыль визита пересчитывается.
5. Manager видит услуги и специалистов с систематическим перерасходом.

### UC-06. Импорт поверх существующей CRM

1. Owner загружает CSV по предоставленному шаблону.
2. Система определяет типы данных, показывает mapping колонок и предварительный результат.
3. Строки валидируются без изменения данных.
4. Owner подтверждает импорт.
5. Валидные записи создаются/обновляются идемпотентно; ошибки доступны отдельным файлом.
6. Повторная загрузка того же набора не создаёт дубликаты.

#### 8.6.1. Алгоритм прогнозирования v1

1. Берутся последние четыре завершённых сопоставимых визита клиента в той же категории услуг.
2. Если есть минимум два интервала, используется медиана интервалов.
3. Если доступен один интервал, используется он, ограниченный диапазоном услуги.
4. Если истории недостаточно, используется `default_return_days` основной услуги.
5. Если на визите несколько услуг, основной считается услуга с наибольшей длительностью; при равенстве - с наибольшей выручкой.
6. Результат ограничивается настройками `min_return_days` и `max_return_days` услуги.

Confidence:

- `high`: минимум три интервала, разброс не более 20%;
- `medium`: два интервала или разброс 20–40%;
- `low`: один интервал либо fallback на настройку услуги.

Пересчёт выполняется после создания, завершения, отмены, корректировки или импорта визита.

#### 8.7.1. Ранжирование waitlist v1

Кандидаты получают баллы:

- точное совпадение услуги: +40;
- предпочтительный мастер: +20;
- полное попадание в желаемый интервал: +20;
- клиент отмечен как last-minute: +10;
- длительность слота покрывает услугу без окна более 15 минут: +10;
- у клиента уже есть пересекающаяся запись: исключить;
- клиент заблокирован или не дал согласие на канал: исключить.

При равном результате выше находится запись, созданная раньше. Формула должна храниться как версия, чтобы изменения не ломали аудит прошлых решений.

#### 8.8.1. Финансовые формулы

```text
service_revenue = сумма цен услуг и add-ons после скидки

material_cost = сумма(actual_quantity × unit_cost_snapshot)

master_commission =
  percent_of_revenue: service_revenue × rate
  fixed: fixed_amount
  percent_after_materials: max(0, service_revenue - material_cost) × rate

contribution_margin =
  service_revenue
  - master_commission
  - material_cost

margin_percent =
  contribution_margin / service_revenue × 100

profit_per_hour =
  contribution_margin / actual_duration_hours
```

Правила:

- при нулевой выручке `margin_percent` возвращается как `null`, а не бесконечность;
- при отсутствии фактической длительности используется плановая, а результат помечается как estimate;
- отсутствующий расход материала не считается нулевым: визит получает флаг `incomplete_cost_data`;
- округление отображения выполняется до 2 знаков, вычисления используют decimal либо integer minor units;
- фиксированные расходы, аренда, utilities и CAC в contribution margin MVP не входят;
- корректировки завершённого визита создают новую версию financial snapshot и audit event.

- первая версия коннектора обязана документировать поддерживаемое направление для каждого поля: inbound, outbound или local-only.

## 9. Бизнес-правила и состояния

### 9.1. Жизненный цикл записи

```text
tentative
  ├──> confirmed ──> completed
  │         │
  │         ├──> cancelled
  │         └──> no_show
  └──> cancelled
```

- переход из `completed` обратно запрещён;
- исправления завершённого визита выполняются через versioned adjustment;
- `cancelled` и `no_show` не занимают слот;
- повторное открытие отменённой записи не допускается: создаётся новая связанная запись.

### 9.2. Жизненный цикл recovery case

```text
open → notified → booked → realized
  ├──────> expired
  └──────> closed_manual
notified ─> open       (предложение истекло, слот ещё актуален)
booked ───> open       (замещающая запись отменена, слот ещё актуален)
```

### 9.3. Attribution

- rebooking attribution window: 14 дней после клика либо 30 дней после отправки, что наступит раньше;
- slot recovery связывается напрямую с исходным `recovery_case_id`;
- одна запись может иметь один primary attribution source;
- ручное редактирование attribution доступно Owner/Manager и журналируется;
- финансовый эффект считается после завершения визита, не после клика или бронирования.

### 9.4. Конкурентные запросы

- создание и подтверждение записи используют транзакционную блокировку слота;
- повторный запрос с тем же idempotency key возвращает первый результат;
- при конфликте API возвращает `409 SLOT_UNAVAILABLE` и актуальные альтернативы;
- webhook и фоновые jobs обязаны быть safe-to-retry.

## 12. API

### 12.1. Стиль и общие правила

- JSON REST API под `/api/v1`;
- авторизация через secure, httpOnly, sameSite cookie для web и bearer token для интеграций;
- timestamps в ISO 8601 UTC; локальное отображение выполняется клиентом;
- money: `{ "amount": 12550, "currency": "MDL" }`;
- пагинация cursor-based: `limit` максимум 100, `next_cursor`;
- фильтры передаются query parameters;
- mutations принимают `Idempotency-Key` там, где возможен повтор;
- optimistic locking использует `If-Match` или поле `version`;
- ошибки имеют стабильный `code`, локализуемое UI-сообщение и `field_errors`;
- API никогда не отдаёт секреты интеграций и object storage keys напрямую.

Пример ошибки:

```json
{
  "error": {
    "code": "SLOT_UNAVAILABLE",
    "message": "The selected time is no longer available",
    "request_id": "req_01...",
    "field_errors": [],
    "details": {
      "alternative_slots": []
    }
  }
}
```

## 14. Рекомендуемая архитектура

### 14.1. Подход

Для MVP рекомендуется **modular monolith**: один backend deployment с чёткими доменными модулями. Это уменьшает операционные расходы и сохраняет возможность выделить messaging, imports или analytics позже.

```text
Responsive Web App
       │
       ▼
API / Backend for Frontend
       │
       ├─ Identity & Organization
       ├─ Clients & Catalog
       ├─ Booking & Visits
       ├─ Retention
       ├─ Slot Protection
       ├─ Costing
       ├─ Reporting
       └─ Integrations
       │
       ├──────── PostgreSQL
       ├──────── Object Storage (photos/imports)
       ├──────── Queue / Scheduled Jobs
       └──────── External adapters
                   └─ Email / SMS / WhatsApp provider
```

### 14.2. Рекомендуемый стек

Стек может быть заменён при сохранении контрактов и NFR.

| Слой | Рекомендация |
|---|---|
| Frontend | TypeScript, React/Next.js, responsive web |
| Backend | TypeScript modular monolith, REST API |
| Database | PostgreSQL |
| Jobs/queue | Managed queue + scheduler либо PostgreSQL-backed queue для пилота |
| File storage | S3-compatible object storage |
| Cache/locking | PostgreSQL advisory/row locks; Redis только при доказанной необходимости |
| Auth | Managed identity provider или проверенная auth library; MFA для Owner как P1 |
| Observability | Structured logs, error tracking, metrics, request IDs |
| Deployment | Managed EU region, separate dev/staging/production |

### 14.3. Модули backend

Модули общаются через application services и domain events, но не обращаются напрямую к чужим таблицам из handlers. Финансовые snapshots и audit events являются append-only. Provider-specific код находится только в adapters.

## 15. Нефункциональные требования

### 15.1. Производительность

- p95 чтения API без отчётов: ≤ 500 ms при пилотной нагрузке;
- p95 mutations: ≤ 800 ms без учёта внешнего messaging provider;
- Dashboard за период до 12 месяцев: ≤ 2 s p95;
- поиск клиента: ≤ 500 ms при 50 000 клиентах в организации;
- старт CSV-импорта до 100 000 строк: ≤ 5 s, обработка асинхронная;
- UI показывает feedback для действий дольше 300 ms.

### 15.2. Надёжность

- целевая доступность пилота: 99.5% в месяц;
- автоматические backups БД не реже одного раза в сутки;
- RPO ≤ 24 часа, RTO ≤ 8 часов для MVP;
- операции бронирования и импорта идемпотентны;
- ошибки внешнего messaging provider не приводят к потере записи или повторной отправке без контроля;
- все фоновые задания допускают безопасный повтор.

### 15.3. Безопасность и privacy

- TLS для всех соединений;
- пароли, если используются, хешируются Argon2id/bcrypt с актуальными параметрами;
- session cookies: `Secure`, `HttpOnly`, `SameSite=Lax/Strict`;
- CSRF-защита для cookie-authenticated mutations;
- rate limits для auth, public links, imports и webhook endpoints;
- secrets только в secret manager, не в БД и логах;
- шифрование at rest для БД и object storage;
- PII маскируется в логах и error tracking;
- signed URLs для фото с коротким TTL;
- антивирусная/контентная проверка uploads либо безопасная image re-encoding pipeline;
- audit log для ролей, policies, комиссий, финансовых корректировок, consent и exports;
- право на экспорт, исправление и удаление данных реализуется административным workflow;
- удаление клиента анонимизирует PII, но сохраняет обязательные агрегированные финансовые записи;
- retention policy: raw notification content 12 месяцев, audit 24 месяца по умолчанию; уточнить с юристом;
- privacy impact assessment и тексты согласий утверждаются до production-пилота.

### 15.4. Accessibility

- целевой уровень WCAG 2.1 AA для основных flow;
- контраст текста минимум 4.5:1;
- полная клавиатурная навигация основных форм;
- label/description/error для каждого поля;
- focus management для modal/dialog;
- screen reader announcements для статуса сохранения и ошибок.

### 15.5. Совместимость

- последние две стабильные версии Chrome, Safari, Edge, Firefox;
- mobile Safari и Chrome Android;
- минимальная ширина 360 px;
- graceful degradation при блокировке third-party cookies;
- приложение не зависит от установки PWA.

### 15.6. Observability

- structured JSON logs с `request_id`, `organization_id`, `user_id` без PII;
- error tracking frontend/backend;
- метрики: latency, error rate, queue depth, job failures, webhook failures, notification delivery, import failures;
- алерты для error spike, exhausted retries, messaging webhook failure и backup failure;
- product events версионируются и не содержат прямых контактов клиента.

### 15.7. Rollout и rollback

- production rollout выполняется сначала для одной внутренней demo-организации, затем для 1–2 design partners и только после этого для всех участников пилота;
- автоматические retention- и waitlist-рассылки по умолчанию выключены и включаются per organization после проверки шаблонов и consent;
- интеграции, automatic campaigns и новый алгоритм расчёта метрик защищаются feature flags;
- при сбое messaging adapter новые отправки ставятся на паузу, а записи и финансовые данные продолжают работать;
- изменения схемы БД используют backward-compatible expand/migrate/contract подход; destructive migration запрещена в одном релизе;
- rollback приложения выполняется на предыдущую совместимую версию без отката уже записанных бизнес-событий;
- ошибочные financial snapshots исправляются новой версией и пересчётом агрегатов, а не удалением истории;
- до каждого schema release проверяется восстановление staging из свежего backup;
- массовую кампанию можно остановить, но уже переданные внешнему провайдеру сообщения могут быть недоступны для отзыва. Это явно показывается пользователю.

## 17. Критерии приёмки MVP

### 17.1. Сквозной сценарий A: прибыльность

**Given** настроены услуга 600 MDL, комиссия мастера 40% и рецептура 35 MDL  
**When** визит длительностью 90 минут завершён без скидки  
**Then** система показывает:

- выручка: 600 MDL;
- комиссия: 240 MDL;
- материалы: 35 MDL;
- contribution margin: 325 MDL;
- margin: 54.17%;
- profit per hour: 216.67 MDL;
- те же значения доступны в визите и Dashboard.

### 17.2. Сквозной сценарий B: rebooking

**Given** у услуги цикл 28 дней и у клиента нет достаточной истории  
**When** визит завершён 1 августа 2026  
**Then** ожидаемая дата равна 29 августа 2026, confidence = low, а напоминание создаётся по настройкам организации.

**When** клиент открывает действующую ссылку и выбирает свободный слот  
**Then** создаётся запись с source `rebooking`, повторное подтверждение не создаёт дубль, forecast получает статус `rebooked`.

### 17.3. Сквозной сценарий C: Slot Protection

**Given** запись на 15:00 отменена в пределах late cancellation window и есть два waitlist-кандидата  
**When** Manager запускает предложение  
**Then** оба получают уникальные ограниченные по времени ссылки.

**When** первый клиент подтверждает слот  
**Then** создаётся одна запись, второй получает `SLOT_UNAVAILABLE`, recovery case становится `booked`.

**When** замещающий визит завершён на 700 MDL  
**Then** `realized recovered revenue` увеличивается на 700 MDL.

### 17.4. Сквозной сценарий D: импорт

**Given** CSV содержит 1 000 валидных и 20 невалидных строк  
**When** пользователь валидирует и подтверждает импорт  
**Then** 1 000 строк обработаны, 20 ошибок доступны с номером строки и причиной, а повторный импорт того же файла не создаёт дубли.

### 17.5. Сквозной сценарий E: локализация

**Given** организация использует `ro-MD`, timezone `Europe/Chisinau`, currency `MDL`  
**When** пользователь открывает Dashboard  
**Then** строки отображаются на румынском, сумма форматируется как MDL, локальная дата соответствует часовому поясу, а сохранённые UTC timestamps не изменяются.

### 17.6. Release gate

Релиз допускается, если:

- все P0-требования реализованы либо имеют подписанное исключение product owner;
- критические сквозные сценарии автоматизированы;
- нет открытых дефектов severity 1 и 2;
- tenant isolation и RBAC прошли отдельные negative tests;
- проведено восстановление staging из backup;
- provider webhook signature/idempotency протестированы;
- локализация не содержит missing keys в трёх языках;
- ручной accessibility-check основных flow пройден;
- privacy/consent тексты утверждены ответственным лицом;
- мониторинг, алерты и runbook для инцидента включены.


Сначала фиксируются identity, tenant isolation и snapshots, потому что последующие модули зависят от стабильных IDs и исторических данных. Costing и Retention можно строить параллельно после Core data. Slot Protection зависит от календаря и уведомлений. Dashboard подключается к стабильным определениям метрик, а не задаёт их сам.

## 20. Зависимости и открытые решения

До начала этапа 3 должны быть приняты решения:

| ID | Решение | Влияние |

## 21. Риски и меры снижения

| Риск | Вероятность/влияние | Мера |
|---|---|---|
| Слишком сложный ввод рецептур | Высокая/Высокое | Шаблоны, мастер первичной настройки, bulk edit, показатель полноты данных |
| Низкое качество данных из CRM | Высокая/Высокое | Validation preview, mapping, idempotency, error export, ручные corrections |
| Нет доступного API конкурента | Высокая/Среднее | CSV-first и универсальный Import API, не связывать core с провайдером |
| Клиенты подтверждают слот, но не приходят | Средняя/Высокое | Короткий срок подтверждения, reminder, история надёжности и повторный запуск waitlist |
| Сообщения блокируются или дороги | Средняя/Высокое | Provider abstraction, frequency cap, email fallback, delivery analytics |
| Неверные финансовые ожидания | Средняя/Высокое | Называть показатель contribution margin, показывать формулу и completeness |
| Double booking при гонке | Средняя/Критическое | DB transaction/constraint, idempotency, E2E concurrency tests |
| Privacy-инцидент с фото/контактами | Низкая/Критическое | Consent, signed URLs, least privilege, audit, PII-safe logs |
| Scope creep в generic CRM | Высокая/Высокое | Любая функция должна улучшать retention, slot recovery или costing KPI |

## 22. Definition of Done для функции

Функция считается завершённой, если:

1. выполнены функциональные acceptance criteria;
2. backend проверяет tenant и role permissions;
3. обработаны loading, empty, validation, permission, conflict и provider error states;
4. добавлены unit/integration tests пропорционально риску;
5. добавлены analytics event и audit event, если применимо;
6. строки доступны на ru/ro/en без missing keys;
7. интерфейс проверен на 360 px и desktop;
8. нет PII в логах;
9. документация API и бизнес-правил обновлена;
10. product owner и QA приняли сценарий на staging.

## 24. Итоговая продуктовая граница

MVP считается успешным не тогда, когда в нём есть полный календарь или CRM, а когда владелец может увидеть и доказать цепочку:

```text
визит завершён
→ клиенту рассчитан следующий визит
→ клиент возвращён или отменённый слот заполнен
→ материалы и комиссия учтены
→ реальная contribution margin отражена на Dashboard
```

Любая новая функция до пилота должна напрямую поддерживать хотя бы одно звено этой цепочки. Если не поддерживает, она переносится за границу MVP.
