# Nail Profit OS

Costing-first SaaS для nail-мастеров и небольших студий. Текущий инкремент закладывает Phase 1 foundation из `nail-profit-os-mvp-roadmap.md` и канонический финансовый сценарий Gate 2.

Приложение использует плоскую структуру без `src`: маршруты находятся в `/app`, общие модули — в корневых `/components`, `/db`, `/domain`, `/i18n` и `/lib`.

## Локальный запуск

Требования: Node.js 22+, npm 11+, Docker.

```bash
cp .env.example .env
docker compose up -d
npm install
npm run db:generate
npm run db:migrate
npm run db:verify-rls
npm run dev
```

Откройте `http://localhost:3000`, создайте аккаунт и организацию Solo или Studio.

Локальный контейнер публикует PostgreSQL на порту `55432`, чтобы не конфликтовать с типичной локальной установкой на `5432`.

## Проверки

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

Юнит-тесты не требуют ничего кроме Node. Интеграционные работают против настоящего PostgreSQL и запускаются отдельно:

```bash
npm run test:integration
```

Им нужны поднятый `docker compose up -d`, отдельная база `nail_profit_test` и применённые в ней миграции. `TEST_DATABASE_URL` и `TEST_MIGRATION_DATABASE_URL` обязательны; запуск жёстко отклоняется, если test URL совпадает с development URL или имя базы не заканчивается на `_test`. Каждый тест очищает test-базу целиком, поэтому файлы идут последовательно, а не параллельно. Тесты ходят **ролью приложения** `nail_profit_app`, чтобы RLS действительно применялась: проверять изоляцию подключением, которое её обходит, бессмысленно. Очистка и подготовка данных идут отдельным подключением владельца — эти два подключения намеренно разведены.

Сквозные тесты — третий набор, с теми же требованиями к базе:

```bash
npm run test:e2e
```

Они вызывают настоящие route handlers с настоящей сессией Better Auth: регистрация, организация, каталог, визит — всё через HTTP-границу, как это делает браузер. Подменён ровно один шов: `next/headers` работает только внутри запроса Next.js, поэтому заголовки приходят из хранилища, куда клиент кладёт cookie очередного запроса. Всё остальное — сессия, проверка прав, tenant-транзакция и её RLS — то же самое, что уходит в production.

Таблица маршрутов читается из файловой системы, а не выписана руками: рукописная разъезжается с деревом при первом же новом endpoint, и набор молча перестаёт что-то покрывать. Неизвестный путь роняет тест, а не проходит мимо.

`npm run test:all` запускает все три набора.

`npm run build` читает `.env`, потому что серверные модули валидируют переменные окружения при импорте. Без `.env` сборка падает на этапе сбора данных страницы `/app`.

## Архитектурные инварианты

Соблюдаются в коде сегодня:

- деньги хранятся целыми minor units (`600 MDL` = `60000`);
- денежное округление симметрично: убыток округляется до той же величины, что и равная ему прибыль;
- убыточная услуга показывается убыточной — маржа и прибыль в час не зажимаются в ноль, а процент маржи при нулевой цене равен `null`, а не нулю;
- неизвестная стоимость материала не трактуется как ноль: расчёт возвращает `incompleteCostData` с причинами и **без единой цифры маржи** (ТЗ §8.8.1, основа списка CST-010);
- финансовый результат содержит `formulaVersion` и объяснение исходных значений;
- основные таблицы несут `version` для optimistic locking и `created_by`/`updated_by` (ТЗ §11.1);
- названия услуг хранятся с переводами (`jsonb` по локалям), а `resolveLocalizedText` реализует fallback LOC-008: запрошенная локаль → язык организации → английский;
- tenant-owned таблицы содержат `organization_id` и защищаются PostgreSQL RLS с `FORCE ROW LEVEL SECURITY`;
- приложение подключается ролью `nail_profit_app` без `SUPERUSER`; миграции используют отдельный owner URL;
- пароли хешируются Argon2id с параметрами минимума OWASP (`m=19456, t=2, p=1`), ТЗ §15.3;
- auth-эндпоинты под rate limit; вход — 10 попыток за 5 минут, регистрация и сброс пароля — 5 за час;
- ответы API следуют ТЗ §12.1: ошибка — `{error:{code, message, request_id, field_errors}}`, успех — `{data, request_id}`, поля snake_case;
- `code` в ошибке стабилен и служит ключом перевода; `message` — английский fallback для неизвестных клиенту кодов;
- матрица прав ТЗ §6.1 закодирована в `domain/rbac.ts` и является единственным источником истины: enum ролей в БД выводится из неё, поэтому разъехаться они не могут;
- приглашения хранят только hash токена (правило одноразовых токенов ТЗ §12.3); сам токен показывается один раз при создании;
- приглашение выписано на адрес, а не на предъявителя: принять его может только аккаунт с тем же email;
- выдача ролей проходит через ту же матрицу — manager не может выписать приглашение с ролью owner;
- изменения ролей пишутся в `audit_event` (ТЗ §15.3) внутри той же транзакции, поэтому запись не переживёт откат операции;
- запрос восстановления доступа отвечает одинаково для существующего и несуществующего адреса, поэтому форму нельзя использовать для проверки, у кого есть аккаунт;
- ссылка восстановления живёт час, одноразова и никогда не возвращается в ответе API — в отличие от токена приглашения, который выдаёт авторизованный участник;
- экспорт и удаление данных доступны только владельцу (ТЗ §6.1) и оба пишутся в `audit_event` (ТЗ §15.3);
- удаление организации не удаляет финансовую историю: организация помечается `deleted_at`, PII клиентов/специалистов/приглашений и незавершённых импортов анонимизируется, членства снимаются, а визиты и financial snapshots сохраняются — ТЗ §15.3 требует именно это, и FK на организацию стоят `restrict` ровно ради истории;
- удаление требует повторного ввода названия организации — «административный workflow» из ТЗ §15.3, а не одна кнопка;
- выгрузка содержит все tenant-domain сущности, включая клиентов, визиты, snapshots, каталоги и import/audit history, но никогда не содержит hash токенов приглашений;
- количества материалов хранятся целыми milli-units (тысячные базовой единицы), как деньги — в minor units;
- себестоимость считается напрямую из цены и размера упаковки и округляется **один раз**: умножать округлённую цену базовой единицы значит умножать и ошибку округления;
- один материал без цены делает рецептуру неполной целиком — частичная сумма выглядела бы как настоящая себестоимость;
- материалы услуги и её опций сливаются в одну строку на материал **до** расчёта: из одного флакона наливают один раз, а два округления вместо одного дают расхождение (66.66 против 66.67 на 100 MDL за 3 мл);
- дельты опций знаковые и могут увести цену или длительность за ноль — тогда расчёт отказывается считать, а не выдаёт бессмыслицу;
- завершённый визит хранит снапшоты цены, названия, комиссии и закупочной цены материала, поэтому изменение каталога завтра не переписывает прибыль вчерашнего визита;
- в визите снапшотится **пара «цена упаковки + объём упаковки»**, а не округлённая цена единицы: округлённая цена, умноженная на количество, округляет дважды;
- `financial_snapshot` защищён триггером БД: `UPDATE` и `DELETE` отвергаются, корректировка пишется новой версией (ТЗ §8.8.1). Это не соглашение, а ограничение — молчаливая правка переписала бы прибыль прошлого месяца;
- отсутствующий фактический расход не считается нулём и блокирует маржу, а отсутствующая фактическая длительность заменяется плановой с пометкой estimate — ТЗ §8.8.1 обходится с этими пробелами по-разному, и код тоже;
- телефон клиента нормализуется в E.164 (LOC-005), а уникальность контактов — частичная: дублей нет, но клиент без телефона допустим;
- отчёт берёт **только последнюю версию** снапшота каждого визита: сложить все версии значило бы посчитать каждую корректировку дважды;
- выручка неучтённых визитов показана отдельно и не попадает в знаменатель маржи — иначе маржа занижалась бы и выглядела как реальное падение;
- средняя маржа считается как сумма маржи ÷ сумма выручки (ТЗ §8.9.1), а не как среднее из процентов: визит на 20 MDL не должен весить как визит на 600.
- область `scope: "own"` из матрицы §6.1 применяется на деле: мастер видит только связанного с собой специалиста и его комиссию, потому что у специалиста есть `user_id`;
- новое правило комиссии закрывает предыдущее той же области датой начала нового: `active_from` включительна, `active_to` исключительна, поэтому передача происходит без разрыва и без наложения, а запрос на прошлую дату по-прежнему находит правило, действовавшее тогда;
- запись в общий каталог (материалы, цены, рецептуры, мастера, правила комиссий) требует области `all`: матрица §6.1 даёт мастеру `materials: write`, но со `scope: "own"` — это списание по своим визитам, а не правка каталога, по которому считаются все;
- услуга без заданной рецептуры считается неполной, а не бесплатной: SRV-007 требует предупредить, а не выдать маржу, посчитанную как будто материалы ничего не стоят;
- область `own` опирается на связь мастера с аккаунтом (`specialist.user_id`), и эта связь выставляется в продукте, а не в БД: у аккаунта не больше одного мастера — частичный уникальный индекс, иначе «свои визиты» зависели бы от порядка строк;
- мастер видит только тех клиентов, кого обслуживал: связь — визит, поэтому список нельзя расширить, угадав id;
- детали импорта — это строки самого файла, поэтому читать их может только роль, которая вправе этот файл импортировать: для клиентского файла обход был бы телефонами и именами в обход §6.1;
- дорогие и угадываемые endpoint'ы `/api/v1` под собственным rate limit: загрузка импорта — 10 в час, подтверждение — 20, приём приглашения — 10; лимит проверяется **до** чтения тела, иначе двухмегабайтный файл всё равно был бы разобран, а отказ не двигает окно вперёд, иначе клиент в цикле запирал бы себя навсегда;
- логи — одна строка JSON на событие с `request_id`, `organization_id` и `user_id` (ТЗ §15.6), и маскирование не зависит от дисциплины вызывающего: `redact` чистит и по имени поля, и по значению — адрес маскируется внутри сообщения об ошибке, внутри URL и на третьем уровне вложенности;
- маска несёт короткий тег (`[email#9f2a]`): две строки лога можно соотнести между собой, но адрес из них не восстановить — защищает усечение до четырёх шестнадцатеричных символов, а не стойкость функции;
- серверные ошибки уходят в `onRequestError` — единственное место, которое видит их все: и упавший handler, и серверный компонент, и action; query string при этом отбрасывается, потому что параметр фильтра — самый обычный способ занести телефон в лог;
- две активные брони (`pending_confirmation` и `confirmed`) не могут пересечься у одного мастера или рабочего места — это exclusion constraint в PostgreSQL, а не соглашение в коде; отменённая бронь пересекаться может, иначе освобождённый слот нельзя было бы продать заново;
- проверка занятости и запись брони идут в одной транзакции под одним advisory lock: проверка, коммитящаяся отдельно от записи, которую она разрешает, не разрешает ничего;
- статусы `cancelled`, `completed` и `no_show` терминальны: запоздавший запрос не может отменить отмену, о которой клиенту уже сообщили;
- одна бронь закрывается ровно в один визит — частичный уникальный индекс по `visit.booking_id`, потому что прикладная проверка «а не завершена ли уже» проигрывается гонкой, а результат гонки — двойная выручка в каждом отчёте;
- бронь и ручной визит закрываются одной функцией: одинаковость финансовых snapshots из Gate 7 нельзя гарантировать двумя путями, её можно только не нарушать одним;
- версия сверяется в `WHERE` самого `UPDATE`, а не сравнением после чтения: двое, открывшие одну карточку, оба прочитали версию 1, и право утверждать, что что-то изменилось, есть только у того, чей `UPDATE` нашёл строку;
- `verify-rls.sql` содержит структурную проверку: любая таблица с `organization_id` без включённой, форсированной политики RLS роняет проверку. Drizzle не генерирует RLS, и это единственное, что ловит забытую политику на новой таблице.

Соотношение документов: **ТЗ (`docs/nail-profit-os-mvp-technical-spec.md`) — источник истины для доменной модели, формул и семантики; roadmap — для границ объёма.** ТЗ описывает полную версию 1.1 и включает в MVP календарь, retention, кампании и waitlist, которые roadmap §3.3 намеренно отложил. При конфликте объём решает roadmap, смысл — ТЗ.

## Заложено, но ещё не подключено

Ниже — код, который присутствует в репозитории, но пока не участвует в рантайме. Это осознанная подготовка следующих фаз, а не работающие гарантии:

- **Удаление одного клиента** — организация-wide erasure уже анонимизирует PII всех клиентов и сохраняет визиты/snapshots. Отдельного endpoint для запроса одного клиента пока нет; его нужно добавить, если такой workflow войдёт в пилот.
- **Удаление аккаунта пользователя** — реализовано удаление данных организации, а не учётной записи. Пользователь переживает удаление организации и может создать новую; отдельный запрос на удаление аккаунта в ТЗ §4.3 не описан и не реализован.
- **Retention policy** — ТЗ §15.3 задаёт 24 месяца для audit и 12 для содержимого уведомлений. Автоматической очистки нет: `audit_event` растёт неограниченно.
- **Доставка приглашений** — почтового транспорта в MVP нет, поэтому токен возвращается пригласившему в ответе на создание и передаётся сотруднику вручную. Ссылку строит клиент. При появлении транспорта токен должен перестать уходить в тело ответа.
- **Доставка ссылок восстановления.** Вернуть токен в ответе значило бы отдать доступ любому, кто назовёт чужой адрес. В development ссылка печатается в локальный лог; в production при `NOTIFICATION_PROVIDER=resend` она отправляется email через тот же provider interface. URL не попадает ни в application log, ни в provider idempotency metadata: ключ строится из SHA-256 URL. Production с `log` по-прежнему падает с `PASSWORD_RESET_TRANSPORT_MISSING`, а не делает вид, что письмо ушло.
- **Хранение токена сброса** — Better Auth держит его в `verification.identifier` в открытом виде (TTL один час). Правило «в БД только hash» из ТЗ §12.3 сформулировано для публичных ссылок; переписывать хранилище библиотеки ради него не стали, но расхождение сознательное.
- **Одна организация на пользователя** — приглашение нельзя принять аккаунтом, который уже состоит в организации. Политика MVP, а не доменное ограничение; удерживается транзакционной блокировкой в двух местах (создание организации и приём приглашения), схему менять не потребуется.
- **Часовой пояс интерфейса вне календаря** — календарь и карточка записи показывают местное время локации по её собственному IANA-имени. Остальные экраны (визиты, отчёт) по-прежнему форматируют даты поясом браузера: для дат визитов это незаметно, но правилом это не является.
- **i18n интерфейса** — словарь RU/RO/EN (`i18n/dictionary.ts`) полон и типизирован так, что пропущенный ключ не компилируется, `resolveLocale` берёт язык организации, `<html lang>` из него же. Чего нет: **личного** языка участника (весь тенант читает на языке организации) и маршрутизации локали в URL — сменить язык можно только в настройках организации, и это меняет его всем. Локализация бизнес-данных (`i18n/localized-text.ts`) рабочая. Пункт «RU/RO/EN» из Фазы 4 выполнен на уровне тенанта, но не на уровне пользователя.
- **`version` как `If-Match`** — optimistic locking работает на записях: карточка, перенос и переходы сверяют версию в `WHERE` самого `UPDATE` и отвечают `VERSION_CONFLICT` с текущим значением. Но версия передаётся полем тела, а не заголовком `If-Match`, как предполагает ТЗ §12.1; остальные сущности версию по-прежнему только инкрементируют, не сверяя.
- **`toMoneyJson` (`domain/money.ts`)** — сериализатор денег из ТЗ §12.1 определён и покрыт тестами, но пока ни один endpoint не отдаёт деньги. Контракт зафиксирован заранее, чтобы Фаза 2 не изобретала свой.
- **Каталог материалов для мастера** — ТЗ §6.1 даёт мастеру «фактическое списание по своим визитам» и молчит о том, вправе ли он просматривать справочник материалов, из которого выбирает. Закодировано по более узкому прочтению; нужно продуктовое решение до Фазы 2.
- **Rate limit** — хранилище in-memory и у Better Auth, и у лимитера `/api/v1`: счётчики у каждого инстанса свои. Для пилота на одном инстансе это верно; при горизонтальном масштабировании нужны общие счётчики, иначе лимиты перестанут значить то, что написано. Остальные endpoint'ы `/api/v1` не ограничены: они требуют сессии и не тратят заметных ресурсов — лимит нужно ставить там, где запрос дорог или где угадывают токен.

`scripts/verify-rls.sql` проверяет структурно: любая таблица с `organization_id` обязана иметь включённый и форсированный RLS с политикой, иначе прогон падает. Единственное задокументированное исключение — `membership`. Негативный тест «контекст не установлен → ноль строк» входит в набор.

## Фаза 7 (в работе)

Online Booking. Entry Gate 7 — коммерческий и пока не пройден: messaging provider выбран (Resend), но ещё требуются пройденный Gate 6 и три платящие организации, готовые пустить в пилот реальные клиентские записи. Код пишется за feature flag, как того требует §7.11, и до прохождения gate публичная страница не включается ни для кого.

Завершены 7.1–7.5 на уровне разработки; технический hardening 7.5 зафиксирован как complete, а реальный rollout управляется [отдельным pilot runbook](docs/operations/booking-pilot-runbook.md). Public booking остаётся за `PUBLIC_BOOKING_ENABLED`, по умолчанию выключенным, отправка уведомлений — за `NOTIFICATIONS_ENABLED`, а каждый арендатор — за собственным уровнем раскатки. Gate 7 не считается пройденным до реальных результатов пилота.

Раздел API §7.6 также реализован: все девять public и девять internal route-групп присутствуют, public surface проходит через общий rate/security guard, staff surface — через membership/RBAC, а три обязательные мутации сохраняют `Idempotency-Key`. Контракт и правила совместимости вынесены в [Online Booking API contract](docs/booking-api-contract.md) и удерживаются отдельным executable contract test.

Раздел уведомлений §7.7 реализован полностью на уровне приложения: outbox и scheduler дополнены production-адаптером Resend и подписанным webhook endpoint. События `sent/delivered/delayed/bounced/complained/failed/suppressed` проверяются по raw body через Svix, дедуплицируются по `svix-id` и применяются по provider timestamp, поэтому повтор или поздно пришедшее старое событие не откатывает текущий статус. В БД сохраняются только внутренние id, тип и время события — без получателя, темы и тела письма.

Время. Расписание говорит «по средам с 09:00», запись говорит «в этот момент», и два дня в году это не взаимно однозначно: час в марте не существует, час в октябре случается дважды. `domain/timezone.ts` называет оба случая (`gap` и `ambiguous`) вместо того, чтобы угадывать, и делает это через базу часовых поясов самого рантайма — таблица смещений руками устаревает в тот день, когда страна двигает стрелки. Смена 02:00–10:00 в Кишинёве длится семь реальных часов в марте и девять в октябре, и это проверено, а не подразумевается.

Данные 7.1: локация со своим IANA-поясом (у студии на два адреса он может отличаться), рабочие места, связи «мастер ↔ локация» и «мастер ↔ услуга» с переопределением длительности, настройки записи на локацию, недельные правила графика и разовые исключения. Все семь таблиц tenant-scoped с forced RLS — `verify-rls.sql` проходит. Локальное время в правилах хранится минутами от полуночи: движок складывает их с длительностями и буферами, а целое число — тот тип, на котором арифметика определена.

Движок 7.2 детерминирован и не читает ни часы, ни базу: `now`, строки и настройки приходят значениями. Порядок операций — из §7.3: недельный шаблон → плюс `available`-исключения, минус `unavailable` → минус занятое с буферами → сетка шага → минус lead time и окно вперёд. Сетка выравнивается по локальной полуночи, а не по началу смены: клиент читает 09:00 и 09:15, и смена, начавшаяся в 09:07, не должна сдвигать все опубликованные времена дня на семь минут. Выходной побеждает пересекающееся «поработаю позже»: из двух утверждений об одном часе исполняется то, которое не даёт записаться.

API 7.1 на месте: локации с настройками записи, недельные графики, разовые исключения и связи мастера с адресами и услугами. Публикация страницы и часовой пояс адреса — решения уровня организации (§6.1 отдаёт organization_settings владельцу), рота — общая на организацию, а собственное время мастер блокирует сам: область own из §6.1 здесь становится правом заблокировать свой день и никакой чужой.

Неизвестный часовой пояс не принимается: расписание, написанное против пояса, которого рантайм не знает, молча интерпретировалось бы как UTC, и весь день предлагался бы не в те часы. Пересекающиеся интервалы в одной роте отклоняются, а не сливаются: человек сказал о своём дне что-то противоречивое, и слияние прячет ошибку до первой записи клиента.

Замена роты повторяет приём правил комиссий: то, что уже действовало, закрывается датой начала новой роты и остаётся в истории — запись, принятая в августе, была предложена по августовскому графику. То, что ещё не начало действовать, заменяется целиком: закрытие правила его же датой начала оставило бы строку, не действующую ни один день, — это и уронило матрицу прав, когда роту заменили дважды за день.

Матрица §6.1 выросла до 52 сочетаний и снова сработала как задумано: одиннадцать новых endpoint'ов не прошли проверку полноты, пока для каждого не была выписана строка с правами.

51 сценарий на движке и алгебре интервалов, включая оба перехода DST, плюс сквозной тест конфигурации: то, что API сохранил, читается движком и даёт ровно те слоты.

Защита от двойного бронирования (7.5) стоит в четыре слоя, и каждый закрывает то, чего не видят остальные: движок не предлагает занятое; transaction-level advisory lock по паре «мастер + локальный день» сериализует конкурентов; проверка внутри этого лока смотрит и брони, и живые holds — две таблицы, поэтому ни один констрейнт не увидит обе; exclusion constraint по `tstzrange(starts_at, ends_at, '[)')` отказывает в пересечении на уровне PostgreSQL. Последний слой единственный, который нельзя забыть в будущем коде, — ради этого он и существует.

Проверено мутацией: с отключённой прикладной проверкой сто параллельных попыток занять один слот всё равно оставляют ровно одну бронь — её удерживает констрейнт. С включённой проверкой те же сто попыток дают одну бронь и девяносто девять внятных `SLOT_UNAVAILABLE`.

Полуоткрытые интервалы важны именно здесь: `10:00–11:30` и `11:30–13:00` — два клиента подряд, а не двойная запись, и exclusion constraint написан тем же `'[)'`, что и вся остальная арифметика фазы.

Hold живёт пять минут и держит слот, пока клиент вводит имя. Истечение нельзя выразить в констрейнте — `now()` не immutable и не может стоять в предикате индекса, — поэтому просроченный hold гасит следующий же запрос по этому мастеру, а то, чего никто не трогает, подбирает `npm run ops:booking-maintenance` раз в минуту.

`Idempotency-Key` обязателен на создании: повтор с тем же ключом и тем же телом возвращает исходную бронь, а с другим телом — 409. Заявка на ключ пишется до брони и в той же транзакции, поэтому две одновременные повторные отправки блокируются на уникальном индексе и дают одну запись, а не две. Отказ по занятому слоту несёт ближайшие свободные времена: проигрыш в гонке — момент, когда клиент вероятнее всего бросит запись, и в ответе должно быть, что делать дальше.

Жизненный цикл записи (первая половина 7.3) закрыт: карточка с историей изменений, подтверждение, перенос, отмена, неявка и завершение в визит. Таблица переходов выписана руками, и интереснее в ней пустые ячейки: `cancelled`, `completed` и `no_show` — терминальные. Запрос, пришедший вторым, не может отменить отмену — клиенту уже сказали, что записи нет.

Завершение брони не дублирует ручной ввод визита, а вызывает ту же функцию: Gate 7 требует, чтобы `booking → visit → profit` давал те же snapshots, что и ручной flow, и единственный способ это гарантировать — один код на два входа. Из брони приходят услуга, опции, мастер и клиент; вводится только то, что знает сама встреча, — фактическая длительность и фактический расход.

Одну бронь нельзя закрыть в два визита: частичный уникальный индекс по `visit.booking_id`. Проверено мутацией — с отключённой таблицей переходов и снятой проверкой версии десять параллельных завершений всё равно оставляют один визит, девять получают 409 от индекса. Двойная выручка во всех отчётах — именно то, что он предотвращает.

Перенос защищён так же, как создание, но берёт два лока — на день, откуда запись уходит, и на день, куда приходит: освобождаемый слот становится продаваемым в момент коммита. Локи берутся в отсортированном порядке, иначе два переноса, меняющиеся днями, встали бы в deadlock. Проверка пересечений при этом игнорирует саму переносимую бронь — запись не может конфликтовать с тем местом, где она уже стоит.

`version` обязателен на переносе и необязателен на подтверждении и отмене. Разница не в аккуратности, а в том, что ловит повтор: второе подтверждение отвергает таблица переходов, а второй перенос ловить нечем — он молча перепишет время, которое кто-то только что согласовал с клиентом.

Причина отмены — код из закрытого списка, не свободный текст: §7.9 держит PII вне колонок брони, а поле, которое администратор заполняет во время разговора с клиенткой, — ровно то место, куда попадает номер телефона.

Календарь сотрудника — три вида вместо сетки часов. На 360 px колонка на мастера нечитаема, а §7.8 требует, чтобы мобильная ширина работала, а не терпелась: день — список по мастерам, неделя — список по дням, плоский список — то, в чём администратор ищет. Из карточки записи доступны подтверждение, перенос, отмена с причиной, неявка и завершение в визит; блокировка времени мастера — там же, отдельной формой.

Каждое время на экране — местное время локации, а не браузера. Конвертация делается на сервере по IANA-имени самой локации, потому что у студии на два адреса они могут различаться, а форматирование в браузере тихо сдвинуло бы всем вторник. Обратно — теми же функциями `domain/timezone`, что и в движке доступности: несуществующее местное время (ночь перевода стрелок) форма отклоняет вместо того, чтобы округлить вперёд и записать клиента на час, который студия не выбирала.

Статус нигде не передаётся только цветом (§7.8): полоса слева дублирует слово, а не заменяет его.

Отказ по занятому слоту показывает ближайшие свободные времена прямо в форме — и показывает их в поясе локации. `toISOString().slice(11,16)` здесь соблазнителен и неверен: летом это на три часа мимо, и студия предложила бы клиенту время, когда она закрыта.

Публичный happy path 7.3 закрыт. `/book/{organization_slug}` отдаёт только опубликованные локации и безопасный каталог, показывает цену, длительность и timezone до контактов, считает слоты для конкретного мастера или детерминированного «любого», удерживает выбранное время пять минут и создаёт запись без аккаунта клиента. Телефон нормализуется, согласия версионируются, повторный confirm защищён `Idempotency-Key`; raw hold/manage token возвращается браузеру один раз и в PostgreSQL не попадает. Mobile layout рассчитан от 360 px, действия и слоты имеют touch target не меньше 44rem.

7.4 закрыта. После подтверждения клиент получает `/booking/{manage_token}`: страница показывает актуальные локальные дату, время, адрес, мастера, состав и цену, разрешает перенести запись только на слот из Availability Engine и отменить её после отдельного подтверждения. Обе операции используют optimistic version, оставляют audit/product events и не делают терминальную запись активной снова. Manage token purpose-bound, хранится как SHA-256 hash, имеет TTL 180 дней и может быть отозван. Ссылка гаснет тем же `PUBLIC_BOOKING_ENABLED`, что и публичная страница: rollback §7 выключает поверхность целиком, а не наполовину.

Перенос по ссылке перестал прятать собственный час записи. Доступность считалась так, будто переносимая бронь занимает своё же время, — и клиент с записью 10:00–11:30 не мог сдвинуться на 10:15, хотя ровно это и просят чаще всего. Теперь `SlotQuery` знает, какую бронь исключить, и то же исключение действует в альтернативах, которые видит администратор при конфликте.

Verification (§7.2, шаг 7). Пока её не было, публичная форма писала в клиентскую базу со слов анонимного посетителя: известный контакт находил существующего клиента и переписывал ему имя, email и язык. Код из шести цифр привязан к hold — не к сессии и не к контакту отдельно, — хранится только как SHA-256 hash с солью из id этого hold, живёт не дольше самого hold и переживает пять неверных попыток. В production с Resend он доказывает владение нормализованным email; ответы намеренно неинформативны и не раскрывают, существует ли клиент (§7.9). Режим включается на локацию; при включённом hold живёт дольше на время доставки кода.

Outbox теперь доставляет. Три транзакции на сообщение вместо одной: claim (`for update skip locked` — два инстанса делят очередь, а не дерутся за её голову), подготовка (чтение брони и выпуск свежей manage-ссылки), финализация. Попытка списывается при claim, поэтому процесс, убитый на середине провайдерского вызова, не крутит сообщение вечно. Временная ошибка возвращается через 1, 5, 25 минут и час; постоянная (адрес, который провайдер отверг) не повторяется вовсе; исчерпанные попытки уходят в `dead_letter`. `NOTIFICATIONS_ENABLED=false` ставит отправку на паузу, ничего не удаляя, — это rollback §7 дословно.

Messaging provider выбран: **Resend**. Production-адаптер отправляет plain-text email через `POST /emails`, передаёт логический ключ outbox в `Idempotency-Key`, ретраит rate limit, 5xx и конкурентный idempotent request, но не повторяет invalid address/credentials/payload. Provider message id сохраняется в outbox; API key, адрес и тело не логируются. `log` остаётся только для локальной разработки.

Resend не отправляет SMS, поэтому production public flow явно email-only для доставки: профиль страницы объявляет `notification_channel=email`, email становится обязательным, verification code привязывается к нормализованному email, а booking notifications ставятся в очередь только по email. Телефон остаётся обязательным клиентским контактом и ключом существующего MVP, но невозможные SMS не создаются и не копятся в `dead_letter`.

Напоминание — не второй планировщик, а строка очереди с будущим `scheduled_at`: диспетчер и так отправляет только то, что подошло по времени. Интервал настраивается на локацию (по умолчанию 24 часа), время старта входит в ключ идемпотентности, а перенос и отмена снимают неотправленное напоминание — клиент не получает напоминание о встрече, которой не будет. Запись за два часа до визита напоминания не получает: момент напомнить уже в прошлом, а «напоминание» сразу после подтверждения — это второе подтверждение.

Сотрудник больше не молчит. Подтверждение, перенос, отмена и создание записи администратором ставят те же шаблоны, что и публичный путь, — из `applyStaffTransition`, а не из четырёх копий в роутах, поэтому пятое действие не сможет уехать без уведомления. Потерянную ссылку выдаёт `POST /api/v1/bookings/{id}/manage-link`: токен уходит клиенту через тот же outbox и не появляется на экране сотрудника.

Джоб отправки — `npm run ops:notifications`. Разделение намеренное: какие арендаторы имеют что отправить — один SQL по всей базе, работа для migration-роли; во что превратить строку — каталог на трёх языках, пояс локации и свежая manage-ссылка, работа для приложения. Скрипт спрашивает первое и просит второе у `POST /api/v1/ops/notifications`, который аутентифицируется общим секретом: cron с чужой сессией — это учётная запись, которую никто не ротирует. Без `OPS_API_TOKEN` endpoint'а просто нет. `ops:booking-maintenance` дополнительно возвращает в очередь сообщения, застрявшие в `processing` после падения процесса, ставит отмену клиенту по протухшей заявке и чистит завершённые verification-вызовы.

Начало 7.5 — раскатка по арендаторам. Environment-флаг выключает модуль во всём окружении, но §7.11 требует закрыть public и calendar routes флагом *на организацию*, а откат §7 — гасить публичную страницу и внутренний календарь по отдельности. Поэтому у организации три уровня: `off`, `calendar`, `public`. По умолчанию `calendar` — у всех, кто существует сегодня, календарь уже есть, и дефолт `off` отобрал бы его на деплое. `public` поднимает оператор после security и concurrency gates (`pilot:ops -- booking-access`), потому что это момент, когда страница становится доступна посторонним; вниз владелец может шагнуть сам — откат, который нельзя выполнить в два часа ночи, не откат. Понижение до `calendar` гасит и страницу, и клиентские manage-ссылки; `off` закрывает ещё и календарь — но только на запись. Откат §7 обещает, что уже подтверждённые записи остаются доступны сотрудникам в read-only, и это не формальность: тумблер дёргают утром, на которое уже записаны двадцать человек. Спрятать список тогда не отменит ни одной записи — это лишь означает, что за стойкой никто не знает, кого сегодня ждать. Поэтому на `off` чтение отвечает, запись отдаёт 404 `BOOKING_DISABLED`, календарь показывает те же дни без единого действия, а вкладка остаётся на месте: она ведёт на настоящую страницу, а не в пустоту.

«Все новые public и calendar routes закрыты feature flags» — утверждение про каждый маршрут, а e2e-набор проверяет только те, для которых кто-то написал сценарий. Отказ здесь не в неправильной проверке, а в отсутствующей: следующий endpoint появляется рядом с одиннадцатью, у которых проверка есть, и не краснеет ничего. Поэтому граф импортов читается целиком — от каждого route-файла обходятся локальные импорты, и в замыкании обязан оказаться модуль, который действительно сравнивает `organizations.booking_access`. Достижимость, а не буквальный вызов: на публичной стороне гейт лежит на три модуля глубже, роут просит каталог, каталог просит организацию, и уровень сравнивается только там. Обратная половина того же утверждения — маршрут вне этой поверхности, работающий с таблицами модуля, обязан быть явным исключением; сейчас оно одно, удаление клиента, потому что §7.9 должен человеку удаление его данных независимо от того, на каком уровне студия держит записи.

Проверка сразу нашла пять незакрытых маршрутов: графики, исключения, локации, booking-settings и привязку мастера к адресу. В пути нет слова `booking`, но именно они решают, что модуль предлагает, — выключенный модуль не может продолжать принимать правки к ним.

Вторая половина §7.11 — expand/migrate/contract. Откат это откат приложения, а не базы: миграция уже применена и обратно не поедет, поэтому предыдущая версия кода обязана работать на новой схеме. Один класс операторов от этого дорог не так, как выглядит: колонка, удалённая в том же релизе, который перестал её писать, превращает «выкатить старую сборку» из тридцати секунд в восстановление из бэкапа — в самый неудачный момент, чтобы это выяснить. Проверка читает `drizzle/*.sql` и требует, чтобы миграция либо оставляла предыдущую версию работающей, либо говорила, почему нет: строкой `-- not-backward-compatible: <причина>`. Это не способ пройти проверку, а её смысл: contract-шаг законен, ломается он тогда, когда его делают в одном релизе с expand и незаметно. Два исторических файла оставлены как есть и перечислены в тесте — применённая миграция это история, и правка её под правило, придуманное позже, сделала бы так, что файл перестал описывать реально выполненное.

Accessibility и локализация (§7.12) проверяются по разметке, а не по рендеру: рендерера в проекте нет намеренно — логику вынесли из компонентов, чтобы её можно было тестировать без него, — а «у каждого контрола есть имя» это свойство исходника, а не конкретного рендера. Разбор идёт компилятором TypeScript по всем 41 `.tsx`: контрол без label/aria-label, кнопка без доступного имени, `form-error` без `role="alert"`, `img` без alt. Первый же прогон нашёл четыре неподписанных поля в таблицах (видимой подписью была строка таблицы, а screen reader читает ячейку отдельно) и девять сообщений об ошибке, которые никак не объявлялись; всё исправлено. Проверка мутацией: снятый `role="alert"` роняет тест.

Локализация проверяется с двух сторон: в клиентских экранах не должно быть текста, которого нет в словаре (разрешены название продукта и самоназвания языков — «Română», переведённая на русский, сделала бы переключатель бесполезным), а в румынском и английском словарях не должно остаться кириллицы — это ловит копипасту при переводе, которую проверка полноты ключей увидеть не может. Мобильная ширина проверяется по CSS: 44 единицы на основные touch targets при действующем масштабе `1px = 1rem` и отсутствие фиксированных ширин, ломающих 360 px.

Это пол, а не сертификат: порядок обхода с клавиатуры, видимость фокуса и живой screen reader проверяет человек, и §7.12 требует этого отдельно.

§7.12 называет уровень «Unit/property», а property-тестов в репозитории не было. Примеры в `availability.test.ts` описывают случаи, которые выбрал человек: смена, начинающаяся в 09:07, воскресенье с переводом часов, буфер, съедающий последний слот дня. Но вход движка — это пять независимых измерений (недельный шаблон, разовые исключения, занятое время, пять настроек и часовой пояс), и интересные отказы живут там, где два из них встречаются. Поэтому сформулированы правила, которые движок обязан соблюдать на любом входе: слот целиком лежит внутри открытого времени, не раньше lead time, не пересекается с занятым с учётом буферов, стоит на локальной сетке и ведёт обратно ровно к тому же инстанту, а результат не растёт, когда растут буфер, длительность услуги, lead time или число занятых интервалов. Генератор — seeded последовательность на десяток строк, а не зависимость: отказ обязан воспроизводиться из самого файла, и seed в сообщении это вся репродукция.

Монотонность стоит прочитать дважды. «Больший буфер не может добавить слот» звучит слишком очевидно, чтобы это проверять, и это ровно форма ошибки знака: вычесть там, где имелось в виду прибавить, — и движок начнёт предлагать *больше*, когда студия просит больше места. Ни один отдельный пример этого не покажет, потому что каждый ответ по отдельности выглядит правдоподобно.

Проверка мутацией нашла дыру в самой проверке. Снятый пропуск несуществующего локального времени не уронил ничего: чтобы это проявилось, смена должна быть открыта ровно в тот час, когда часы двигаются, а триста случайных сценариев такого не собрали ни разу. Дни переходов пришлось построить руками — восемь пар «пояс + дата», включая получасовой сдвиг Lord Howe и два контрольных пояса без перехода вообще. После этого та же мутация роняет сразу два свойства: сетку и уникальность. Всего проверено четырьмя мутациями — снятый lead time, инвертированный знак буфера, `contains` вместо `overlaps` и переставленный порядок исключений, — каждая роняет то свойство, ради которого написана.

Bot challenge (§7.9) включается порогом, а не всегда. Клиент, который просто записывается, не видит его никогда: считаются отказы — rate limit, неверный код, попытка удержать время, которое никогда не предлагалось, — и после десяти за десять минут публичные мутации (hold, verify, создание) требуют решённой задачи. Чтения не требуют ничего: посетителя, сравнивающего время, нельзя заставлять что-то вычислять, а объём чтений и так ограничен лимитами.

Задача — proof of work, а не CAPTCHA-вендор, и дело не в брезгливости. CAPTCHA — третья сторона посреди flow, который должен работать на 360 px в трёх языках, она отправляет адрес и поведение клиента тому, кого студия не выбирала, и Entry Gate 7 такого вендора не выбирал. PoW стоит атакующему измеримого CPU на попытку и обычному клиенту — доли секунды: шестнадцать бит это ~65 000 хешей. Nonce подписан HMAC и несёт собственный срок, поэтому перезапуск процесса не забывает выданные задачи и не начинает принимать поддельные; потраченные nonce держатся в памяти, потому что proof of work, который можно переиграть, ничего не доказывает. Подпись привязывает задачу к вызывающему — решённую нельзя передать на другой адрес. Это не защита от арендованной фермы и не претендует ею быть: за это отвечают лимиты, TTL hold'а и код подтверждения. Это то, что делает дешёвый флуд недешёвым.

Наблюдаемость §7.10 — `npm run ops:booking-metrics`. Отчёт считает то, что выводится из базы: записи по статусам и источникам, конверсию holds, глубину очереди и dead letters, общий provider acceptance и отдельно долю сообщений, переданных не позже двух минут после `scheduled_at`, job lag (насколько задержалось самое старое сообщение, у которого уже подошёл срок), исходы верификации и конверсию `booking → visit`. Отдельным запросом проверяется инвариант Gate 7 «ни одна пара активных bookings не пересекается» — не доверяя exclusion constraint, а спрашивая данные; тест на это специально снимает констрейнт и вписывает пересечение мимо приложения, потому что проверка, которая всегда возвращает ноль, не проверка. Непройденный критерий — ненулевой код возврата, чтобы отчёт можно было поставить в проверку, которая обязана краснеть.

Задержек в database-отчёте нет, и это не пропуск: p50/p95 запроса не восстанавливаются из таблиц — строка брони не помнит, сколько её писали. Поэтому шесть измеряемых маршрутов (публичный поиск слотов, создание, перенос и отмена, staff-создание и staff-перенос) обёрнуты `timedRoute` и печатают `http.timing` с длительностью и статусом. Экспортированные JSONL-логи проверяет `npm run ops:booking-latency -- --file <path> --min-samples 30`: он считает fleet-level p50/p95, требует достаточную выборку и возвращает `NOT_READY`, если p95 availability выше 500 ms или booking mutations выше 800 ms.

Runbook 7.5 фиксирует preflight, настройку Resend, подготовку tenant, demo smoke, волны `demo → design_partner → first_paid`, ежедневную эксплуатацию, Gate 7 evidence и точный rollback. Код provider готов; внешний пилот остаётся **No-Go**, пока в целевом окружении не подтверждены sending domain, `RESEND_API_KEY`, `RESEND_FROM` и реальная sandbox-доставка.

Cookie-аутентифицированные маршруты закрыты от cross-site (§7.6). JSON-only API само по себе отбивает классическую атаку — кросс-сайтовая форма умеет только `urlencoded`, `multipart` и `text/plain`, а хендлер, читающий JSON, отвечает на них 422, — но `multipart/form-data` принимает загрузка импорта, и «в этой версии библиотеки cookie по умолчанию SameSite» не контроль, за который кто-то в репозитории отвечает. Поэтому сессия просто не засчитывается на запросе, который браузер пометил как cross-site: `Sec-Fetch-Site` шлют все актуальные браузеры и подделать его страничным JS нельзя, `Origin` — запасной вариант, а запрос без обоих (curl, job, тест) не браузер и амбиентной cookie не несёт. Проверка стоит в `getActiveMembership` — единственной функции, которую и так зовут все двадцать шесть хендлеров, включая ту самую загрузку.

Security-матрица §7.12 закрыта отдельным набором из 14 сценариев: hold-токен не открывает бронь (purpose в хеше), подменённый префикс организации и подменённый секрет не аутентифицируют, истёкший и отозванный токены перестают работать, hold одной студии не превращается в бронь на странице другой, сотрудник чужой организации получает 404. Неразличимость проверяется побайтово: неизвестный slug, страница на паузе и организация, откаченная до `calendar`, отдают идентичный конверт с точностью до `request_id` — иначе 404 становится справочником студий. Запрос кода подтверждения одинаков для существующего клиента и для незнакомого номера. Бакеты rate limit проверены на раздельность: исчерпанная верификация не закрывает страницу тому же посетителю, а отказ несёт `Retry-After`. И то, что записано на диск: audit-события публичной брони не содержат ни телефона, ни email, только `has_email`, а в таблице токенов лежат только SHA-256 хеши.

Concurrency-наборы §7.12 дополнены до пяти: к «ста параллельным попыткам», holds и истёкшим holds добавились общее рабочее место, гонка двух переносов на один слот и десять одновременных повторов одного запроса с одним `Idempotency-Key`.

Набор с рабочим местом сразу нашёл дефект, которого не видел ни один из существующих. Advisory lock брался по паре «мастер + день», поэтому два *разных* мастера, бронирующих одно кресло, брали два разных лока, доходили до вставки одновременно и вставали друг на друге при проверке exclusion constraint по `workplace_id` — PostgreSQL снимал обе транзакции с 40P01 вместо того, чтобы отдать одну бронь и один `SLOT_UNAVAILABLE`. Теперь лок берётся на каждый занимаемый ресурс, ключи сортируются перед взятием (иначе два переноса, меняющиеся местами, соберут deadlock уже на самих локах), и двадцать параллельных попыток занять одно кресло оставляют ровно одну бронь.

Проверки 7.4: 11 интеграционных сценариев на конечный автомат очереди (ретраи, backoff, dead letter, идемпотентность, пауза, напоминание, «бронь уже неактивна»), E2E на verification (в том числе «код подтверждён для одного номера — бронь под другим отклонена»), на молчание сотрудника, на job и на перенос внутри собственного часа, плюс прогон самого maintenance-скрипта против настоящей базы — его SQL написан руками, и переименованная колонка иначе всплыла бы уже в production.

Отдельно исправлена изоляция тестов: integration/E2E требуют `TEST_DATABASE_URL` и `TEST_MIGRATION_DATABASE_URL`, имя базы с суффиксом `_test` и fail-fast при совпадении с development DB. Поэтому `resetDatabase()` больше не может удалить локального пользователя или сессию из `nail_profit`.

## Фаза 5 (техническая часть завершена)

Сквозные сценарии ТЗ §17 автоматизированы — это первый пункт release gate §17.6.

Сценарий A (прибыльность) проходит от регистрации: организация, мастер с комиссией 40%, материал 100 MDL за 10 мл, услуга 600 MDL на 90 минут, рецептура на 3.5 мл. Карточка услуги, закрытый визит и dashboard дают одни и те же шесть чисел — 35.00, 240.00, 325.00, 54.17%, 216.67. Раньше это подтверждалось руками на живых данных; теперь падает на CI.

Сценарий D (импорт) гоняет 1 000 валидных и 20 битых строк через multipart-загрузку: колонки распознаются по русским заголовкам без правки mapping, каждая битая строка отчитывается номером строки в файле и причиной, повторная загрузка того же файла даёт `created: 0, updated: 1000`, а повторное подтверждение уже применённой задачи — 409.

Жизненный цикл визита закрыт отдельно: корректировка пишет версию 2 и не трогает версию 1, dashboard считает только последнюю, а подорожавший вдвое материал не переписывает закрытый визит — но следующий считает уже по новой цене.

Матрица прав проверяется на уровне API: 40 сочетаний «метод + endpoint» × четыре роли, те же маршруты без сессии (39 отказов и явно публичный health-check) и 12 попыток достать чужую организацию по id. Ожидания выписаны из §6.1 руками, а не выведены из `domain/rbac.ts`: тест, который берёт ожидание из проверяемого модуля, согласится с любой его ошибкой. Полнота держится отдельной проверкой — новый endpoint, для которого никто не выписал строку, роняет набор.

Матрица нашла три дефекта, и все три исправлены.

`specialist.user_id` читался в шести местах и не записывался нигде. Область «только свои» из §6.1 работала правильно и не относилась ни к кому: приглашённый мастер входил в пустой продукт и получал `FORBIDDEN` при попытке закрыть визит. Появились `PATCH /api/v1/specialists/{id}`, связка в интерфейсе мастеров и частичный уникальный индекс — один аккаунт, один мастер.

Список клиентов не фильтровался по области: мастер видел всех клиентов организации вместе с телефонами, хотя §6.1 даёт ему «только назначенные клиенты/визиты». Теперь связь — визит.

Детали импорта отдавали строки файла любому участнику. Для файла клиентов это имена и телефоны в обход запрета аналитику на PII; теперь чтение задачи требует того же права, что и её применение, а история импортов фильтруется по сущностям, которые роль вправе импортировать.

Оба исправления проверены мутацией: с отключённой фильтрацией клиентов падает тест области, с отключённой проверкой прав на импорт — две строки матрицы.

Лимиты §15.3 доведены до `/api/v1`. Better Auth закрывал только свои маршруты; наши два уязвимых места — импорт, где двухмегабайтный файл декодируется и разбирается трижды до первой записи, и приём приглашения, где попытка угадать токен стоит атакующему один запрос. Ответ 429 несёт `Retry-After`: отказ без него клиент повторяет немедленно и тратит следующее окно впустую.

Логи стали структурными и без PII (§15.6, §15.3). Маскирование живёт в самом логгере, а не в правиле «не логируйте лишнего»: правило, которое держится на памяти вызывающего, — не контроль, и день, когда его забудут, будет днём, когда список клиентов уедет в агрегатор логов.

Ошибки собираются в `instrumentation.ts`. Обернуть двадцать шесть route-файлов в try/catch — покрыть меньше и разъехаться на двадцать седьмом.

Privacy и consent закрыты versioned-согласием при регистрации: приложение не принимает `false` или отсутствующее согласие, а версию условий, версию privacy notice и серверные timestamps хранит в `user`. Полные пилотные тексты доступны на RU/RO/EN; их выпуск в production требует юридического согласования по `docs/operations/privacy-release-checklist.md`.

Owner получил экспорт и защищённое повторным вводом названия удаление данных организации. Основные экраны получили skip-link, явный focus state, live regions для ошибок, семантические labels и мобильные правила. Проверка реальным Chrome viewport подтверждает на 360 CSS px отсутствие горизонтального переполнения; поля и основные действия формы регистрации имеют высоту около 48 px.

Performance gate автоматизирован на пилотном объёме в 2 000 визитов. Dashboard выполняет три агрегирующих запроса вместо N+1 и в контрольном локальном прогоне загрузился за 35 ms при бюджете 2 s.

Добавлены безопасный `GET /api/health`, security headers, мониторинговые пороги и runbooks для инцидента и восстановления. Локальный backup restore drill создал отдельную БД, восстановил custom-format dump, сверил схему/миграции/критические row counts, выполнил read-транзакцию и удалил временную БД. Проверка на реальном staging и доставка тестового алерта остаются инфраструктурными действиями Gate 5, а не изменениями кода.

## Фаза 6 (инструментарий пилота готов, сбор реальных данных идёт вне репозитория)

Закрытый rollout получил четыре волны: `demo → design_partner → first_paid → extended`. При `PILOT_ACCESS_ENFORCEMENT=true` workspace/API доступны только активной pilot enrollment; `pending` и `paused` сохраняют данные, но fail closed. Operator CLI не открывает следующую волну без `profit_review` предыдущей, блокирует переход при открытом Severity 1–2 issue и требует три проверенных платящих организации перед `extended`.

PII-free product telemetry автоматически фиксирует начало/завершение onboarding, первый достоверный расчёт каждой услуги, завершённый визит и lifecycle импорта. События имеют версию, actor role/source и внутренние entity IDs, а unique key делает повторы API/import идемпотентными для метрик.

`npm run pilot:ops` ведёт оплаты/волны, активные onboarding/support/interview minutes, управленческие решения трёх типов, продления и structured issue register. Read-only `report` вычисляет каждый критерий Gate 6, MRR/ARPA и coverage; неизвестное значение возвращает `NOT_READY`, а не превращается в ноль. Команды и cadence описаны в `docs/operations/pilot-runbook.md`.

Сам Gate 6 остаётся бизнес-результатом: его нельзя закрыть seed-данными или тестами. Нужны десять реальных оплат, использование, решения, двухмесячные продления и измеренная capacity поддержки.

## Фаза 4 (в работе)

Импорт CSV работает целиком: загрузка, сопоставление колонок, превью с валидацией, подтверждение и результат.

Файл читается таким, каким его отдаёт Excel на молдавском ноутбуке: разделитель `;` встречается не реже `,`, кодировка Windows-1251 не реже UTF-8, BOM обычен. Разделитель выбирается разбором, а не подсчётом символов, — запятая внутри закавыченного названия не должна победить. UTF-8 проверяется строго и только потом идёт откат на 1251: 1251 декодирует любые байты, поэтому обратный порядок превратил бы все названия в кракозябры.

Числа разбираются через строки. `parseFloat("240.55") * 100` даёт 24054.999999999996, а весь смысл продукта в том, что арифметике можно верить.

Защита от formula injection стоит на выгрузке, а не на загрузке: переписывать значение на входе значило бы портить данные, которые нас просили сохранить, и всё равно не защитило бы строки, созданные иначе. `toCsv` ставит апостроф, который Excel читает как «это текст». Проверка не трогает обычные числа, иначе каждое отрицательное число в каждой выгрузке ломалось бы.

Повторный импорт не создаёт дублей. Проверено на живых данных: та же выгрузка второй раз дала `created: 0, updated: 4`, каталог остался на 4 материалах и 4 версиях цен — новая версия цены пишется, только если цена действительно изменилась.

Скачанный шаблон загружается обратно без единой ручной правки — этот круг закрыт тестом, потому что если не сходится наш собственный файл, то чужой тем более.

Сырой текст файла хранится между загрузкой и подтверждением, чтобы оба шага читали одни и те же байты, и стирается после завершения: список клиентов — это PII, и §15.3 не даёт причин держать его дальше. Сопоставление и счётчики остаются.

Интерфейс переведён на RU/RO/EN целиком: захардкоженных строк не осталось. Пропущенный ключ — ошибка компиляции, а не найденная на пилоте дыра: русский словарь задаёт набор ключей, остальные локали типизированы как полные записи над ним. Множественное число идёт через `Intl.PluralRules` по каждому языку — русский, румынский и английский не совпадают ни в одной точке.

Язык берётся из организации (ТЗ LOC-008), `Accept-Language` — только для тех, у кого организации ещё нет, и с учётом q-весов. `<html lang>` и описание страницы следуют тому же выбору.

Валюта MDL/EUR меняет то, в чём записываются новые цены, и осознанно ничего не пересчитывает: §8.8.1 стоит на том, что сумма значит ровно то, что значила в момент записи.

Onboarding показывает пять шагов, каждый из которых измеряется, а не отмечается: мастер **с правилом комиссии**, материал **с закупочной ценой**, услуга **с ценой и длительностью**, рецептура, первый визит. Стартовые материалы добавляют девять названий без цен — придуманная закупочная цена и есть тот самый правдоподобный неверный ответ, который §8.8.1 запрещает.

Проверено вживую: девять стартовых материалов не двигают шаг «материал с ценой», а импорт одной строки с ценой закрывает его и обновляет уже существующую «Базу», а не создаёт дубль.

Из Фазы 4 остаётся замер Gate 4 на реальных файлах и пилотных данных: четыре файла через mapping, 99% строк без ручных правок, первый расчёт до 30 минут — это измерения, а не код.

## Фаза 3 (в работе)

Визиты работают целиком: закрытие визита с фактическим расходом, история с фильтрами по периоду и мастеру, версионируемая корректировка.

Форма закрытия подставляет факт по норме — мастер правит только то, что отличается. Это и путь к «меньше 60 секунд» из Gate 3, и то, что делает отклонение осмысленным, а не побочным эффектом пустой формы.

Проверено на живых данных: визит закрыт на 340 MDL, скорректирован до 310 (версия 2, версия 1 цела), после удвоения цены материала старый визит остался 310, а новый посчитан по новой цене — 320.

Dashboard `Studio Ledger` считает выручку, contribution margin, маржу, прибыль в час, сравнение плана и факта по материалам и рейтинг услуг — всё из финансовых снапшотов, с фильтрами по периоду и мастеру.

Проверено на живых данных: сумма последних версий снапшотов в БД (1600 выручки, 730 маржи) совпадает с отчётом до копейки. После корректировки визита отчёт показывает 660 — новую версию, а не сумму обеих.

Из Gate 3 остаются: замер закрытия визита на мобильном под 60 секунд и доля визитов с посчитанной маржой на пилотных данных — это измерения, а не код.

## Фаза 2

Канонический сценарий Gate 2 считается в продукте: материалы с закупочными ценами → услуга с ценой и длительностью → рецептура → разбор расчёта.

```
Цена услуги          600.00 MDL
Комиссия 40%         240.00 MDL
Материалы             35.00 MDL
Contribution margin  325.00 MDL
Margin                54.17 %
Прибыль в час        216.67 MDL
```

Сделано: пересчёт «упаковка → базовая единица», рецептуры с версионированием, правила комиссий с версионированием, API материалов/услуг/рецептур, каталог материалов и карточка услуги с `financial insight panel` и разбором формулы.

Onboarding проходится полностью через интерфейс: регистрация → организация → мастер с комиссией → материалы → услуга → рецептура → расчёт. Ни одного обращения к БД руками.

Не сделано и ждёт очереди: рабочие места (P1), параметры дизайна SRV-005, `Location`, массовое изменение цен SRV-008.

Интеграционные тесты закрывают ограничения PostgreSQL, изоляцию арендаторов, расчёт из реальных строк, imports, outbox/jobs и provider contract. Resend отдельно проверен на success, idempotency, retryable/permanent failures и отказ от неподдерживаемого SMS.

Набор проверен мутацией: со снятым CHECK на количество в рецептуре падает соответствующий тест, с выключенным RLS на `material` падают восемь тестов изоляции. Зелёный прогон означает работающие инварианты, а не отсутствие проверок.
